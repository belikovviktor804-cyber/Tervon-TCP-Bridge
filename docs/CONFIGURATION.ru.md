# Конфигурация Bridge и интеграция с Xray

Источник схемы: `prototype/cmd/bridge/main.go` и `prototype/bridge.go` на коммите `83c9848`. Не используйте примеры как замену действующим конфигурациям.

## Формат

Один JSON-файл передаётся через `bridge -config /absolute/path/config.json`. Неизвестные поля, дополнительные JSON-документы и ошибочные обязательные параметры отклоняются при загрузке.

| Поле | Режим | Значение |
|---|---|---|
| `mode` | оба | `client` или `server` |
| `listen` | оба | локальный адрес `host:port` |
| `cert_file`, `key_file` | оба | leaf-сертификат и приватный ключ соответствующей стороны |
| `ca_file` | оба | PEM доверенного CA противоположной стороны |
| `remote_url` | client | HTTPS URL строго с путём `/v1/stream`, без query/fragment |
| `server_name` | client | проверяемое TLS-имя Decapsulator |
| `service` | client | имя разрешённого сервиса, передаваемое в `Tervon-Service` |
| `max_local_connections` | client | положительный предел одновременно принятых локальных TCP-сессий |
| `routes` | server | сервис → список `{ "Name": "...", "Address": "host:port" }` |
| `authorized` | server | SHA-256 DER клиентского leaf-сертификата → разрешённые сервисы |
| `max_streams` | server | положительный предел одновременно обслуживаемых HTTP/2 потоков |

`routes` задаётся администратором Decapsulator: клиент не выбирает произвольный IP или порт. При нескольких backend используется выбор по кругу с попыткой следующего адреса при ошибке TCP dial. Это не перенос уже открытого TCP-сеанса.

## Текущий подтверждённый маршрут

```text
TervonVPN → Homeserver Xray inbound VLESS XHTTP :55636
→ Xray outbound VLESS TCP TLS (tag tervon-bridge-fi)
→ Encapsulator 127.0.0.1:55635
→ HTTPS/2 + mTLS → finserver Decapsulator
→ finserver Xray VLESS TCP TLS :55535
→ Hysteria2 Germany → Internet
```

**Важно:** Xray VLESS TLS — это протокол внутри TCP-туннеля. TLS 1.3/mTLS между Bridge-процессами — отдельный слой. Сам Bridge не декодирует VLESS и не реализует Hysteria2. На Homeserver Xray-конфигурацией управляет 3x-ui; ручная правка `/usr/local/x-ui/bin/config.json` может быть перезаписана панелью.

Отдельный SOCKS5-эксперимент: локальный `127.0.0.1:55638`, удалённый тестовый вход `:55639`, backend SOCKS5 `127.0.0.1:55538`. Эти порты **не относятся** к основной цепочке и не должны появляться в шаблоне production по умолчанию.

## Экспорт метрик для существующего Prometheus (M1, кодовый этап)

Опциональное поле `metrics_listen` поддерживается в обоих режимах. Пример значения: `"127.0.0.1:19193"` — **только пример**, перед включением необходимо убедиться, что порт свободен. Разрешён исключительно буквальный loopback IP. Не используйте `0.0.0.0`, публичный адрес или hostname.

На отдельном приватном listener доступны:

- `GET /metrics/v1` — исходный JSON-контракт `tervon.bridge.telemetry.v1`;
- `GET /metrics` — формат Prometheus text 0.0.4 с фиксированными метриками `tervon_bridge_*` (счётчики сессий и полезных байтов, backend dial, ошибки с фиксированными причинами, uptime, ready, память, горутины и агрегированные latency). Скорость в Prometheus рассчитывать через `rate(tervon_bridge_upload_bytes_total[1m])` и `rate(tervon_bridge_download_bytes_total[1m])`.

Prometheus может собирать метрики **на том же узле**, где работает соответствующий Bridge, через `127.0.0.1:<metrics_port>/metrics`. Для Finserver требуется отдельная защищённая схема доставки агрегатов до центрального мониторинга; **не открывать loopback endpoint в интернет**. Изменения конфигурации и рестарт рабочих служб выполнять только после backup, тестирования и согласованного отката.

Показатели Padding/Jitter до реализации M2/M3 остаются `NOT_IMPLEMENTED` в JSON и не объявляются активными в Prometheus. Счётчики upload/download отражают **полезные скопированные байты**, а не полный сетевой трафик. Для публичного сайта необходимы серверная авторизация и отсутствие секретов, клиентских IP и содержимого потоков.

**Статус:** исходный код Prometheus-экспорта добавлен в ветке `work/m1-framing`; проверка CI и развёртывание фиксируются отдельно. Наличие кода не означает подключённый мониторинг.

## Безопасность

- Сервер требует клиентский сертификат, доверенную цепочку и разрешение fingerprint → service.
- Клиент проверяет сертификат сервера и TLS-имя; TLS не ниже 1.3, ALPN `h2`.
- Для `listen` клиента предпочтителен `127.0.0.1`, если доступ нужен только локальному Xray.
- Удалённый listener ограничивайте firewall; не публикуйте backend наружу без необходимости.
- Установите разумные положительные пределы соединений/потоков. Пределы не равны полноценным per-IP квотам или защите от DoS.
- Нельзя считать отсутствие ошибок доказательством защиты от DPI, утечек или зависших соединений.

## Что ещё нужно сверить перед релизом

Реальные параметры Decapsulator и точные пути его файлов, правила firewall, фактический TLS SAN, имена сервисов и допустимые значения лимитов. Не публикуйте действующие сертификаты, UUID, токены или внутренние конфигурации без редактирования.
