# Выпуск бинарного релиза

## Подтверждённый артефакт

Homeserver `/opt/tervon-tcp-bridge/bridge`: ELF x86_64, статическая сборка Go 1.25.5, `CGO_ENABLED=0`, размер около 6.5 MB. SHA-256:

```text
5c813bae9cb0c68e3d5ac1e9afb0556f13cb270b369a86ae8ffc0d20adb086e2
```

Встроенная VCS-информация: `83c98482048d130041e89f545db5885ade090f2b`, `vcs.modified=true`. Поэтому этот бинарник можно назвать **сохранённым проверенным экземпляром**, но нельзя утверждать, что он воспроизводится из чистого коммита.

## Перед публикацией

1. Сохранить копию бинарника **в отдельном каталоге артефактов**, не перемещая и не заменяя работающий файл.
2. Сверить `sha256sum` с указанным значением.
3. Выполнить проверку отсутствия встроенных секретов и внутренней инфраструктурной информации; не публиковать содержимое `/etc/tervon-tcp-bridge/`.
4. Согласовать лицензию. Без неё публичная публикация бинарника может создавать неопределённость прав на распространение.
5. Привязать релиз к проверенному Git-коммиту и явно отметить `vcs.modified=true` в release notes.
6. Не называть релиз production-ready без отдельного решения и проверки finserver.

## Создание отдельной копии (не затрагивает службу)

```bash
mkdir -p /opt/tervon-tcp-bridge-lab/release-artifacts
cp -- /opt/tervon-tcp-bridge/bridge \
  /opt/tervon-tcp-bridge-lab/release-artifacts/tervon-bridge-linux-amd64
sha256sum /opt/tervon-tcp-bridge-lab/release-artifacts/tervon-bridge-linux-amd64
```

GitHub Release следует создавать **после** ревизии исходников и разрешения на распространение. Не добавляйте большие бинарники в историю Git без необходимости; предпочтительны assets GitHub Releases.

## Установка будущего релиза

Скачайте бинарник и опубликованный SHA-256, проверьте контрольную сумму до установки. Создайте отдельный каталог версии, подготовьте сертификаты и конфигурацию. Сначала проверьте на изолированном порту, затем принимайте отдельное решение о переключении службы. Не заменяйте файл, на который указывает работающий systemd unit, во время подготовки.

## Откат

Сохраняйте предыдущий проверенный бинарник и его конфигурацию в каталоге версии. При неудачной новой установке возвращайте прежние **пути к версии** в unit и выполняйте переключение только в согласованное окно обслуживания. В рамках документирования никакие действующие службы не изменяются.
