# M6 / Stage 4 — Android-идентичность и PKCS#10 CSR

**Статус на 2026-11-20: файлы созданы в GitHub, НЕ встроены в TervonVPN DPI, НЕ скомпилированы в APK, Android PASS НЕ подтверждён.**

Эти исходники — отдельный пакет для безопасного переноса после чтения *текущих* файлов приложения, а не слепой установщик. Не применять старые rollback/patch-файлы и не изменять рабочее приложение, его механизм подписи, сборки, HEV, Xray или VPN до подтверждения точек интеграции.

## Исходники

- `BridgeDeviceIdentity.kt` — единая локальная индивидуальная ключевая пара EC P-256. Приватный PKCS#8 зашифрован AES-256/128 GCM посредством **неэкспортируемого** симметричного ключа Android Keystore. В файл `noBackupFilesDir/tervon-bridge-device-identity.json` пишутся только SPKI, IV и ciphertext. Чужой/утраченный Keystore-ключ не заменяется незаметно: операция прекращается с ошибкой.
- `BridgeDeviceCsr.kt` — CSR PKCS#10, SHA256withECDSA, PEM `CERTIFICATE REQUEST`; формат принимает существующая Go-функция `xui.SignDeviceCSR`. Не требует нового протокола или кастомной реализации ASN.1.
- `BridgeDeviceSelfCheck.kt` — явная локальная проверка сохранения публичного ключа между экземплярами, подписи challenge и подписи/связности CSR. Это исходник проверки, **не подтверждение**, что тест уже выполнялся.

Пакет Kotlin `com.tervonvpndpi.app`, соответствующий показанным оператором действующим файлам Android.

## Зависимости

Используются штатные Android JCA/JCE, Android Keystore, `AtomicFile`, а для PKCS#10 — **одна** совместимая с текущим Android/Gradle зависимость Bouncy Castle `bcpkix` (она подтянет необходимые криптографические модули того же семейства как транзитивные зависимости). Конкретную поддерживаемую версию выбрать **после просмотра текущего Gradle** и совместимости с minSdk; не внедрять несколько ASN.1 библиотек и не делать собственный ASN.1.

## Почему это не Android Keystore EC-private-key

Релизный Go Bridge v1.0.1 — **отдельный ELF**, который запускается Android `ProcessBuilder` и читает файловый `key_file` через `tls.LoadX509KeyPair`. Он не умеет вызывать неэкспортируемый аппаратный EC-ключ из Android Keystore. Чтобы **не переписывать** рабочий Bridge и не внедрять JNI, текущий вариант использует генерируемый в приложении экспортируемый EC P-256 ключ, зашифрованный при хранении симметричным AES-ключом Android Keystore.

Это осознанное ограничение: пока Go Bridge работает, он должен получить расшифрованный PKCS#8 ключ в закрытом runtime-файле, доступном только приложению, и этот PEM временно существует вне Keystore. `BridgeDeviceIdentity.kt` **не создаёт такой файл**; владелец жизненного цикла должен явно создавать и удалять его, не раскрывая ключ в логах, crash report, Flutter или сети. Утверждать, что приватный EC-ключ «никогда не покидает Keystore», было бы неверно.

## Следующие обязательные компоненты того же M6

1. Сверить текущие `BridgeConfigManager.kt`, `BridgeRuntimeControl.kt`, Gradle и Flutter/Xray маршрутизацию с настоящим исходным кодом на Homeserver; не перезаписывать существующую интеграцию.
2. Подключить имеющийся ключ к **подтверждённо аутентифицированному** API регистрации подписки: клиент передаёт CSR/подпись challenge, сервер проверяет право владения подпиской, затем выдаёт клиентский leaf. Один подписанный CSR или публичный идентификатор подписки **не доказывает** право на выдачу.
3. Доставлять клиентский leaf, доверенную публичную цепочку и настройки HTTPS Bridge по проверенному каналу; секреты CA/3X-UI остаются только на сервере.
4. Безопасно подготовить app-private временный PKCS#8 PEM именно для существующего Go ELF; обеспечить очистку после завершения процесса.
5. Авторизовать отпечаток leaf в постоянном Android Decapsulator без ослабления mTLS и проверить доставку ACL, отзыв и истечение сертификата.
6. После готовности и проверки TLS/HTTP2/alpn, защищённого внешнего сокета через `VpnService.protect()` и готовности локального listener переключать Xray с прямого VLESS на Bridge. При неудаче — восстановление исходного маршрута.
7. На Homeserver собирать APK только после интеграции с исходниками приложения; затем проверять подпись APK и реальный Android E2E.

**Не заявлять PASS** без фактических результатов сборки и мобильных тестов. Действующие Linux Bridge Россия → Финляндия, серверный Xray и Docker Android ingress этим этапом не меняются.
