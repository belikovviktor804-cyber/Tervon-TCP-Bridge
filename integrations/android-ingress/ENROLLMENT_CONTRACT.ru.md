# M6 — привязка Android-устройства к постоянному Decapsulator


## Уточнение: никакой привязки к домену в Android (2026-11-21)

**Последнее прямое решение оператора, приоритетнее секции «Требуемое имя» ниже:** приложение НЕ содержит фиксированных доменов, IP, портов конкретного Bridge, списка серверов или специальных значений для `vp.xrayvless.online`. Имя `vp.xrayvless.online` — только текущий пример пользовательской подписки и администрируемой серверной конфигурации, а не целевой FQDN Android-кода. `bridge.xrayvless.online` — исторический SAN прежней серверной установки.

Пользователь выбирает обычную текущую подписку. Приложение определяет её фактический адрес из уже существующих данных подписки, автоматически выясняет, что **на соответствующем сервере** Bridge настроен и предлагает получение сертификата через существующую доверенную серверную инфраструктуру. Если Bridge отсутствует, никакого получения сертификата нет. Если ранее полученный сертификат этого Bridge ещё действителен, использовать его; иначе создать CSR существующим Stage 4 P-256-ключом и автоматически запросить клиентский mTLS-сертификат, затем сохранить его. Никакого нового пользовательского аккаунта, кнопок регистрации и ручного ввода адреса/ключа. **Обнаружение сервера и доказательство права на выпуск — отдельные требования; доменное имя само по себе не авторизует выдачу.**

Текущий этап M6 ограничен **автоматическим получением/сохранением mTLS-сертификата**. Ни VPN E2E, ни перенаправление Xray, ни выпуск APK не включаются в этот конкретный этап. Смена DNS и серверного TLS SAN для конкретной установки — обычная операция администрирования и НЕ препятствие в архитектуре/коде приложения. Работающие службы не изменены, способ серверного discovery/API не выдумывать без проверки фактического интерфейса.

## Актуальное уточнение оператора — 21.11.2026 (имеет приоритет над устаревшими адресами и расширенным M6)

**Текущая задача — только автоматическая выдача/получение Android-клиентом сертификата mTLS.** Проверка действующего VPN-трафика E2E, переключение Xray, тесты маршрута и прочие этапы сейчас **не входят в этот узкий рабочий шаг**. Существующий Stage 4 `BridgeDeviceIdentity` + `BridgeDeviceCsr` сохраняется; дополнительных ключевых систем, ручного регистрации или каталогов не вводить.

**Требуемое имя:** `vp.xrayvless.online` — домен подписки, по которому Android должен определять наличие настроенного Bridge и получать сведения о возможности регистрации. Прежний `bridge.xrayvless.online` больше **не целевой FQDN** для нового Android Bridge. Это изменение целевого домена, **не свидетельство** обновления DNS, nginx, TLS, Docker или действующего серверного сертификата.

Порядок работы: выбран активный VLESS-профиль, относящийся к `vp.xrayvless.online` → проверено, что Bridge настроен для этого домена → если для этого Bridge нет действующего клиентского mTLS-сертификата, Android автоматически формирует CSR существующим P-256-ключом → сервер выпускает сертификат через существующий `SignDeviceCSR` → Android сохраняет сертификат и серверные параметры для дальнейшего использования. Если Bridge не существует — никакого обращения к регистратору и никаких дополнительных действий. При наличии действующего сертификата повторный выпуск не нужен. Регистрация без пользовательской кнопки.

**Различать обнаружение и право на выпуск:** сам факт наличия `vp.xrayvless.online` в профиле или DNS не является доказательством, что запрос пришёл от действующего подписчика. Нельзя открывать неаутентифицированный публичный центр выпуска mTLS-сертификатов. Использовать реально существующий подтверждённый источник прав; не придумывать дополнительную систему пользователей, новый пользовательский пароль или токен без утверждения. Проверка авторизации и безопасное введение выданного сертификата в действующий ACL остаются необходимыми условиями работоспособности выдачи, но не являются требованием VPN E2E в этой задаче.

**Подтверждённое текущее состояние:** ранее установленный server leaf имеет SAN `bridge.xrayvless.online` и хранится с конфигурацией действующего контейнера. Имеющийся `prepare-production-pki.sh` уже принимает имя FQDN и создаёт сертификат для этого имени, но **отказывается перезаписывать существующий приватный каталог**. В GitHub нет подтверждения выпуска и установки server leaf c SAN `vp.xrayvless.online`; действующий сервер и его ключи не изменять до отдельной проверки безопасного способа замены и согласованного cutover. Ни один исходный файл Go Bridge v1.0.1 не нуждается в изменении для поддержки нового FQDN.

## Постоянная архитектура

- **Режим обхода выключен:** Android → действующий прямой VLESS TCP `:30000`.
- **Режим обхода включён пользователем:** Android Xray → локальный Encapsulator → `https://bridge.xrayvless.online:<approved-port>/v2/stream` → постоянный Docker Decapsulator → существующий Xray `host.docker.internal:30000` → действующая серверная маршрутизация.
- Включение вручную, независимо от Wi-Fi/LTE. Изменения активной VLESS-подписки, UUID, текущего FIN-каскада или Xray для рабочего режима не требуются.

## Безопасная автоматическая регистрация

1. Приложение проверяет, что выбранный профиль — управляемая сервером действующая VLESS-подписка, и получает **подтверждённый из подписки или подписанного серверного метадокумента** адрес регистратора; **не** выводит адрес из произвольного camouflage SNI.
2. Android создаёт индивидуальную приватную ключевую пару и CSR, не отправляя приватный ключ. Сертификат должен быть совместим с файловым PEM-интерфейсом текущего Android Bridge; возможность безопасного использования Android Keystore без экспорта ключа проверить по фактическому JNI/TLS интерфейсу до утверждения реализации.
3. Сервер принимает запрос только после **доказанной авторизации по существующей подписке**. Не считать публичный IP, наличие SNI, знание URL, HWID или сам CSR достаточным основанием для выдачи. Данные для проверки прав брать из действующего источника VLESS-подписок, не хранить второй независимый список пользователей без необходимости. Конкретная интеграция зависит от текущего источника прав доступа на Homeserver — он **ещё не изучен**.
4. Уполномоченный регистратор подписывает CSR отдельным **client CA** из `/etc/tervon/bridge-android/private/client-ca.key`, устанавливает `clientAuth`, короткий ограниченный срок действия, привязку к учётной записи/устройству и квоту устройств. Использовать проверенную библиотеку TLS/X.509, не писать собственную криптографию.
5. Регистратор вносит отпечаток SHA-256 DER подписанного leaf-сертификата в `authorized` **постоянного** Decapsulator для сервиса `vpn`, с атомарным обновлением, журналом и безопасным откатом. Текущий v1.0.1 читает ACL **при старте**, поэтому при добавлении устройства требуется отдельное утверждённое решение: reload только нового экземпляра без потери уже подключённых пользователей либо минимальное безопасное расширение ACL в новом ingress-контуре. Нельзя отключать mTLS или выдавать всем сертификатам CA безусловный доступ.
6. Ответ Android включает только клиентский сертификат, публичную цепочку доверия, проверенный `server_name`, адрес Bridge, путь `/v2/stream`, сервис `vpn` и поддерживаемые параметры Padding/Jitter; **не** содержит CA/private key сервера.
7. Android запускает Bridge, проверяет TLS 1.3, HTTP/2 ALPN `h2`, mTLS и готовность локального входа, лишь затем изменяет маршрут Xray на локальный порт Encapsulator. Внешний сокет Bridge исключается из VpnService через `protect()`. При выключении возвращается обычный VLESS; без ложного статуса «обход активен».
8. Отзыв пользователя/устройства удаляет разрешение из ACL и делает сертификат недействительным на уровне Bridge. Повторная выдача и истечение сертификата должны восстанавливаться без ручного вмешательства; приватный ключ Android не переносится на сервер.

## Два TLS контура, не смешивать

- **Public HTTPS bootstrap:** соединение к регистратору с обычной проверкой публично-доверенного TLS-сертификата/подписанной серверной конфигурации. Нельзя раздавать новый self-signed CA по этому же неаутентифицированному соединению и считать его доверенным.
- **Bridge mTLS:** отдельный уже работающий TLS 1.3 сервер с именем `bridge.xrayvless.online`, доверие к нему должно приходить через защищённый канал регистрации/подписанную конфигурацию. Client-CA серверный приватный ключ не входит в контейнер и не передаётся устройству.

## Актуальное состояние и завершение

Подтверждено: постоянный Docker container `running`, `restart=unless-stopped`, mount `/etc/tervon/bridge-android/config:/config`, host listener `127.0.0.1:18443`, серверный SAN `bridge.xrayvless.online`, VLESS TCP `:30000` доступен из Docker. Тест TLS 1.3 был с **лабораторным**, не production-сертификатом; в production клиентский список пока deny-all.

**Не сделано:** интеграция с реальным источником подписок, registrar API, выдача/отзыв сертификатов, динамическая ACL, согласование способа внешнего HTTPS, Android routing/protect() и реальный E2E.

**Ближайший практический шаг:** выяснить **только источник авторизации действующих VLESS-подписок** (процесс/файл конфигурации Xray/панель либо служба выдачи подписок), не копируя пользовательские UUID и секреты и не меняя живую конфигурацию. После этого реализовать единый законченный пакет M6 enrollment → ACL → Android, а не создавать дополнительные временные службы.


## M6 — серверный API-адаптер 3X-UI (2026-11-20)

Подготовлен изолированный Go-пакет `integrations/android-ingress/xui/`: только HTTPS/GET, чтение уже сохранённого Bearer-токена из приватного файла Homeserver, `List()` и `GetByEmail()`. Поддержаны фактически подтверждённые ответы `obj:[]` и `obj.client:{}`. Ошибки панели приводят к отказу, редиректы запрещены, URL и Bearer-токен не выводятся в ошибках. Тесты с локальной HTTPS-моделью покрывают успешное чтение, неверную авторизацию/URL, ошибки ответа, несовпадение клиента, экранирование. `go test ./...` в отдельном рабочем каталоге: **6 PASS**, но GitHub Actions и запуск на Homeserver ещё не проводились.

**Это API-адаптер, не регистратор и не авторизация телефона.** Пакет не поднимает HTTP-сервер, не пишет в 3X-UI, не подписывает CSR, не трогает ACL или работающие службы. Его нельзя подключать напрямую к Android или публиковать как API без механизма доказательства владения подпиской и проверки квот/сроков. Принципиально не добавляем вторую базу пользователей; сохраняем 3X-UI в качестве источника данных. Вопрос выбора отдельного регистрационного секрета и его защищённой доставки через существующую подписку пока требует утверждения конкретного контракта. Не объявлять M6 PASS до полного E2E.


## M6 — строгая предварительная проверка подписки (2026-11-20)

В серверный пакет `xui` добавлена `CheckSubscriptionEligibility(record, usage, now)` с тестами. Это **только проверка допустимости подписки**, не аутентификация Android и не разрешение сертификата. Не выдавать клиентский mTLS-сертификат по её `nil`-результату без отдельного доказательства владения разрешённым регистрационным секретом, проверки привязки к нужному VLESS inbound, лимита устройств и актуальной ACL.

Проверка отказывает при: пустом/невалидном ID, отключении `enable`, истечении `expiryTime`, отрицательном `expiryTime` (ожидание первой активации), отрицательных лимитах, отсутствии достоверных счётчиков расхода при ограниченной квоте, отрицательных/переполненных счётчиках и достижении лимита. `expiryTime=0` и `totalGB=0` обозначают отсутствие соответствующего ограничения согласно документации 3X-UI; для конкретной установленной версии семантику ещё следует подтвердить. Отдельный `UsageSnapshot` должен поступить из реально проверенного API статистики, **нельзя подставлять нули при ошибке API**. `limitHwid` здесь только валидируется на неотрицательность; контроль числа устройств пока не реализован.
