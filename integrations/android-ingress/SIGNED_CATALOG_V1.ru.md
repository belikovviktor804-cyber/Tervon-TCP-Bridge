# M6 — подписываемый каталог Bridge-серверов v1

**Статус: код изолированно записан; APP_RUNTIME_NOT_INTEGRATED / ANDROID_BUILD_NOT_RUN.** Доверенный ключ ещё не выпущен и не закреплён в APK.

## Формат доверия

Принят вариант 2 — обновляемый **подписанный каталог**, при котором Android заранее доверяет фиксированному публичному Ed25519-ключу подписанта. Этот ключ не должен поступать из самого каталога, произвольной VPN-подписки или camouflage SNI. Приватный ключ подписанта хранится отдельно и никогда не включается в исходники, APK или работающий Decapsulator.

Envelope JSON: обязательные поля `format` (значение `tervon.bridge.catalog.envelope.v1`), `key_id`, `payload_b64`, `signature_b64`. Base64 — standard encoding с padding. Ed25519 подписывает **точные bytes** UTF8("Tervon-Bridge-Catalog-v1") + byte 0x00 + decoded payload bytes. Не требуется неоднозначная JSON-канонизация: подпись сверяется с исходным payload без пересериализации.

Decoded JSON payload строго содержит:
- `version: 1`;
- `serial` — положительный монотонно возрастающий номер;
- `issued_at`, `expires_at` — Unix секунды, окно не более 30 дней;
- `servers` — массив 0–256 записей.

Каждая запись содержит обязательные `id`, `endpoints` (массив выбранных VPN host+port), `tls_name`, `bridge_url` (HTTPS), `enrollment_url` (HTTPS), `server_ca_pem`. CA здесь служит для проверки **TLS-сервера Bridge**, а не для выдачи клиентских сертификатов. Endpoints определяют офлайн-сопоставление профиля с подписанным Bridge-server ID. Дубли ID и host:port, неизвестный ключ, неверная подпись, несовпадающий TLS host, невалидный HTTPS, лишние JSON-поля — отказ. Пустой **подписанный** список серверов позволяет отозвать сразу все сопоставления.

## Локальный кеш и отключённый Bridge

Android получает подтверждённый каталог через будущий защищённый механизм обновления; текущая библиотека **не делает запросов, DNS, выдачи сертификатов или переключения VPN**. Проверенная версия хранится через Android AtomicFile в noBackupFilesDir. Повреждённое или просроченное содержимое не является доверенным. Новая подпись с меньшим `serial` или изменёнными байтами при одинаковом `serial` отвергается. Повторный приём тех же байтов идемпотентен; ошибка обновления не перезаписывает кеш.

При ручном DPI OFF не регистрировать устройство, не обновлять каталог по сети, не пробовать Bridge. При ON офлайн-адрес выбранного VPN-профиля сопоставляется с каталогом и передаётся ранее проверенному `BridgeServerReconciler`. Если сертификата нет — регистрация только отдельной кнопкой пользователя. Ошибка DNS не превращает известный сервер в неизвестный.

## Код и границы проверки

- `stage4/BridgeSignedServerCatalog.kt`: Bouncy Castle Ed25519, строгая проверка подписанного payload и AtomicFile cache.
- `xui/catalog/sign.go`: офлайн-библиотека Go stdlib Ed25519, не работает как HTTP endpoint.
- `xui/catalog/sign_test.go`: проверка подписи, domain separation, tamper rejection и невалидных входов.
- `stage4/install_signed_catalog.py`: только guarded staging Android verifier и reconciler, не заменяет отличающиеся файлы и не трогает действующие службы.

**Остаётся:** подтверждённые Go CI тесты и Android-компиляция; выпуск и pin доверенного публичного ключа; механизм защищённого получения каталога; полная проверка server CA; интеграция с реальным профильным событием и ручной аутентифицированной регистрацией; реальный Xray route + socket protect + rollback и Android E2E. Не заявлять PASS за пределами полученных логов.

Ограничение: serial rollback guard реализован в обычном app-private хранилище. Физический откат данных приложения атакующим с доступом к устройству этим механизмом отдельно не предотвращается.


## M6 — офлайн-выпуск подписанного файла без создания production-ключа

Добавлена команда `xui/cmd/catalog-sign` (в составе прежнего Go-модуля; никаких сетевых интерфейсов или новых служб). Используется существующий **Ed25519 PKCS#8 PEM** из защищённого файла, переданный оператором явно через `-key`; утилита не генерирует и не печатает ключи. Проверяются права файла (никаких разрешений группе/остальным), обычный файл, отказ от символьных ссылок и подмены inode, ограничение размера; для ключа требуется unencrypted PKCS#8. Это означает, что режим `0600` защищает доступ правами ОС, но **не шифрует приватный ключ на диске**: пригодность такого хранения для production и фактическая защищённая директория требуют отдельного решения. Использование выделенного офлайн-носителя/изолированного окружения предпочтительно, процесс запускается только оператором, без постоянной службы.

Пример формы запуска (НЕ выполнять с демонстрационным ключом): `go run ./cmd/catalog-sign -key <защищённый-путь-PKCS8> -payload <проверенный-json> -key-id <утверждённый-id> -out <новый-файл-envelope>`. Выход создаётся только при отсутствии файла, режим `0600`, при ошибке подписи он не создаётся. Утилита подписывает JSON, но не публикует каталог и не утверждает доверие подписанных данных; содержание, serial и CA требуют независимой проверки до подписания.

Изолированный Go 1.23.2 `go test -race -count=1 -v ./...` для эквивалентной локально воспроизведённой команды: 3 теста PASS (правильная подпись, запрет перезаписи, неправильные права и symlink, плохой JSON). Запуск CI по текущему commit и фактическая production-подпись ещё не подтверждены. Не генерировать production-ключ до согласования защищённой среды хранения и процедуры публичного pin в APK; не делать `go run` под пользователем действующего Bridge/Xray.
