# M6 — отдельный входящий Decapsulator для TervonVPN DPI (предварительный пакет)

**Состояние:** исходники и шаблон; **не развёрнут, не испытан**, автоподписка сертификатов и Android-переключение ещё не реализованы. Новые файлы не изменяют Linux Encapsulator Россия → Финляндия, Xray или VLESS TCP :30000.

## Роли

- Android: собственный Bridge **Encapsulator**, локальный TCP-вход для Xray.
- Российский сервер: **новый отдельный** Bridge **Decapsulator** в контейнере, backend — уже существующий VLESS TCP :30000 на хосте.
- Российский сервер → Финляндия: действующий **независимый** Linux Bridge; ничего не меняем.
- Прямой VLESS TCP :30000 остаётся доступным для режима «Обход DPI выключен». Переключение **только вручную**.

## Файлы

- `Dockerfile`: отдельная сборка текущего Linux Bridge из `prototype/` на Go 1.23.
- `compose.yaml`: профилированный, **не запускаемый автоматически** контейнер. HTTPS/2 принимается на :8443 внутри; порт хоста **по умолчанию только 127.0.0.1:18443**. Внешний HTTPS-вход — отдельное решение после проверки.
- `server.json.example`: шаблон конфигурации **без секретов**. `authorized` содержит заведомо фиктивный отпечаток 64 нуля; реального клиента он не авторизует.
- `prepare-local-fixture.sh`: **только лабораторная**, однократная генерация отдельного CA, server/client EC P-256 сертификатов и JSON вне Git. Ничего не запускает; отказывается перезаписывать существующий каталог.

`host.docker.internal:host-gateway` нужен, потому что `127.0.0.1` внутри контейнера не является адресом Homeserver. Xray слушает `*:30000` по наблюдению оператора 2026-11-20, но доступ из контейнера ещё НЕ проверен. Учитывайте правила firewall/DOCKER-USER и ограничивайте разрешённый путь к backend. Не вводите `network_mode: host` ради обхода этой проверки.

## Предварительные условия (не применять к действующим службам)

1. Получить подтверждённый актуальный источник релизного бинарника v1.0.1 и SHA. Текущий Dockerfile собирает исходники текущей ветки и **не доказывает**, что результат идентичен релизу. Перед эксплуатацией закрепить версию/хеш и провести тесты.
2. Выбрать **свободный** внешний HTTPS-порт и TLS-имя, не вмешиваясь в Nginx, Xray, 3x-ui или действующий Bridge. До выбора внешнего входа контейнер слушает только loopback хоста.
3. Создать приватную директорию за пределами Git с `server.json`, `pki/server.crt`, `pki/server.key`, `pki/client-ca.crt`. Права на чтение файлов должны позволять UID 65532 читать необходимые сертификаты/ключ **только** в этом контейнере. CA private key хранится отдельно.
4. На server JSON указать **действительный** SHA-256 DER *leaf* сертификата Android-клиента вместо фиктивных 64 нулей; список `authorized` проверяется при **старте** Bridge, а не обновляется автоматически.
5. Прежде чем публиковать HTTPS, проверить в изоляции: доступ контейнера к Xray :30000, TLS 1.3/h2/mTLS, маршрут `/v2/stream`, двусторонний TCP, отказ недоверенному клиенту, нормальное завершение и журнал без секретов.

```sh
# Только статическая проверка compose, без запуска:
ANDROID_BRIDGE_CONFIG_DIR=/path/to/private/staged/config \
  docker compose -f integrations/android-ingress/compose.yaml \
  --profile android-ingress-manual config
```

Не запускать `up` на production до отдельного утверждённого cutover-плана. Даже при включённом профиле этот Compose не затрагивает действующие службы, но контейнерные правила сети и порты обязаны проверяться перед запуском.

## Будущий Android discovery/enrollment — не реализовано

Пользователь **вручную** включает «Обход DPI». Приложение извлекает адрес и TLS SNI из выбранного VLESS-профиля, **не предполагая**, что SNI всегда принадлежит серверу. Администратор сможет разместить HTTPS discovery-файл с информацией только об Android-входе, не о российско-финском каскаде.

Планируемый порядок: обнаружение → создание локальной ключевой пары устройства → отправка **только публичного ключа/CSR** → проверка разрешения на выпуск → клиентский сертификат → подтверждение владения ключом → конфигурация → старт Bridge → проверка работоспособности → переключение Xray на loopback Bridge. Серверный TLS-ключ, CA private key и приватный ключ телефона никогда не пересылаются.

**Открытый вопрос:** как выдавать сертификаты без создания новой системы аккаунтов и при этом не превращать HTTPS API в публичный анонимный центр выдачи сертификатов. В существующем ядре `authorized` — статическая таблица отпечатков; нулевая ручная настройка **невозможна** без отдельного проверенного обновления ACL нового Decapsulator. Никакой реализации выдачи или перезапуска в данном пакете нет.

При отказе Bridge приложение оставляет прямой VLESS, выводит причину и не отображает ложный статус «активно».

Текст под переключателем: **«Если в вашем регионе нет блокировок VPN, рекомендуем оставить обход DPI выключенным для экономии заряда аккумулятора.»**

## M6 test-only PKI — следующий изолированный этап

На Homeserver исходники уже доступны по SSH в `/opt/tervon-tcp-bridge-m6-android-ingress`. Сначала синхронизировать **только эту ветку**, не действующую установку Linux Bridge. Затем выполнить `bash -n integrations/android-ingress/prepare-local-fixture.sh` и с отдельного согласования запустить:

```sh
sudo bash integrations/android-ingress/prepare-local-fixture.sh /opt/tervon-bridge-m6-lab
```

Каталог `/opt/tervon-bridge-m6-lab` обязан **отсутствовать** до запуска, внутри Git его создавать нельзя. В нём генерируются короткоживущие **тестовые** ключи (`private/`, доступ root), подкаталог `config/` доступен UID/GID 65532 контейнера только для чтения через bind-mount. Скрипт проверяет цепочку и назначение сертификатов, создаёт разрешённый SHA-256 сертификата тестового клиента и JSON, но не открывает порт, не запускает Docker и не подключается к Xray.

При успешном результате ожидается `M6_LAB_PKI=PASS`, `M6_LAB_SERVER_JSON=CREATED`, `M6_LAB_RUNTIME=NOT_STARTED`. Это **не** выпуск клиентских сертификатов Android и **не** рабочая PKI, не использовать для production. Подтверждение успешного локального SSL-соединения и сертификата — следующий отдельный тест. Внешний порт `18443` не публиковать: Compose связывает его только с `127.0.0.1` хоста.

Тестовый CA private key никогда не копировать в контейнер и Android, не отправлять в GitHub или чат; на сервер не передавать реальные client private keys. После испытаний лабораторную PKI удалить только по согласованной процедуре и не смешивать с рабочей инфраструктурой.

**Контроль безопасности:** запуск генератора требует root для создания отдельных ограниченных прав, но не меняет действующие сертификаты `/etc/tervon-tcp-bridge/`. Настоящая регистрация Android должна выпускать сертификат на CSR/публичный ключ, созданный **телефоном**, а не генерировать клиентский приватный ключ на сервере.

## M6: исправление несовместимого Docker-образа (2026-11-20)

При первом запуске тестового контейнера оператор получил `json: unknown field "padding_enabled"`; контейнер завершился, listener `127.0.0.1:18443` отсутствовал. **Причина подтверждена сравнением исходников:** ветка M6 основана на старом `main` (`prototype/cmd/bridge/main.go` без Padding/Jitter), а релизный тег `v1.0.1` содержит Padding/Jitter и `/v2/stream`. Лабораторный JSON верен для релиза. **Нельзя удалять поля Padding/Jitter или переводить клиент на v1.**

Dockerfile теперь отказывает в сборке из старого исходника. Для исправления используйте **отдельное Git worktree** с официальным тегом, не переключая рабочую ветку M6 и не затрагивая действующие службы:

```sh
cd /opt/tervon-tcp-bridge-m6-android-ingress
git pull --ff-only
git fetch --tags origin
git worktree add --detach /opt/tervon-tcp-bridge-m6-release-src v1.0.1

docker build \
  -f /opt/tervon-tcp-bridge-m6-android-ingress/integrations/android-ingress/Dockerfile \
  -t tervon-bridge-android-ingress:local \
  /opt/tervon-tcp-bridge-m6-release-src
```

Это пересобирает **только тестовый образ**; `docker compose up` здесь не вызывается. Предварительно убедитесь, что путь release worktree отсутствует. Поскольку текущая Compose-конфигурация использует ветку M6 как build context, `docker compose build` без специального исправления контекста теперь **намеренно выдаст ошибку проверки версии**, а не незаметно соберёт старый Bridge. Запуск после успешной сборки — отдельный этап с `--no-build`, подтвердить работу контейнера и локальный HTTPS/2/mTLS, не открывая порт наружу.
